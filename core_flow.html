Tool-KG × Mol-Pipeline × Slime-WD 核心流程可视化文档 v3

目标：让项目 owner 可以沿着箭头读完整主流程，并看到每一步的输入、动作、输出、消费者、过滤规则、调试边界与待确认点。本版刻意牺牲简短性，优先讲清细节。

0. 本版采用的“足够细”的描述标准

上一版的问题是节点仍停留在“Stage1/2 构建工具卡与关系图”这种摘要层。这个粒度不足以让 owner 判断流程是否正确。本版每个关键节点都按下面的六格模板展开：

输入是什么

具体到文件、目录、配置、数据行、环境变量、外部服务。例如：skills_full/、stage_taxonomy.json、complete_session.jsonl。

动作做什么

说明算法/脚本的真实工作，而不是只写“处理”。例如：抽 tool card、按 stage prune candidate pair、单向 adjudication、closure 验证。

中间判断是什么

列出过滤、accepted/rejected、debug 与正式路径的判断条件。比如：molclaw_usage > 0、partial edge 需 input closure。

输出是什么

具体到产物名、字段角色、sidecar。比如：tool_cards.jsonl、edge_debug_sidecar.jsonl、mcp_sft_all.train.jsonl。

谁消费它

说明下一步脚本/仓库如何读它，避免产物孤立。例如：KG sampled tasks 被 mol-pipeline/pipeline/kg 消费。

不是它的事情

指出边界。例如：Tool-KG Stage3 不远程执行 MolClaw；Offline ToolRL formal training 不调用 MCP。

读图方式：每个大图先给箭头主链，再给节点展开卡片。箭头表达“数据/产物流”，卡片解释“这个节点内部到底做了什么”。

工具卡里的核心信息

工具卡的作用是让后续 pairwise 判边时有统一的工具语义表示。它不只是“工具名 + 描述”，而是把自然语言 skills、schema、输入输出、任务 stage 转成可以比较的结构。

  • tool identity：规范化工具名、所属服务、功能一句话。
  • input contract：需要哪些参数、参数代表什么科学实体，例如 SMILES、protein sequence、PDB/CIF path、pocket center。
  • output contract：输出能否作为另一个工具输入，例如结构文件、binding affinity、ADMET 属性、candidate ranking。
  • stage tag：使用 stage_taxonomy.json 提供的固定 taxonomy；stage 只用于 pruning，不参与 confidence 打分。
  • evidence：解释性文本写入 tool_cards_debug.jsonl，主图字段瘦身。

为什么先做工具卡

后续关系图不是靠工具名字符串相似度建立，而是比较“上游工具的输出是否能提供下游工具的完整/部分输入、格式转换、参数化、过滤、排序、验证等关系”。工具卡是 pairwise adjudication 的证据材料。

  • 避免直接让 LLM 在长 skills 文档中任意联想。
  • 让每条边有可审计依据。
  • 让 stage pruning 在候选对层面生效，减少无意义 pair。

2.2 Stage2：关系图的边如何建立

输入

  • tool_cards.jsonl

  • rules_v1.yaml

  • 保留 allowed direction
  • 被剪 pair 进入 pair_pruned_by_stage.jsonl
single direction adjudication

  • 每个 allowed direction 独立调用 LLM
  • 判断 A 是否可为 B 提供输入/中间结果/过滤排序等
  • 输出 edge type、confidence、理由
score + export

图产物

  • pair_adjudications.jsonl
  • scored_edges.jsonl
  • graph_core/all/expanded/uncertain/negative
  • edge_debug_sidecar.jsonl

边类型：关系图不是单一“可连接”

当前 edge ontology 包含多种 canonical edge types，用于表达不同的工具依赖关系：

  • generates_full_input_for：上游输出可完整作为下游输入。
  • generates_partial_input_for：上游只提供部分输入，需要其他 provider 补齐。
  • preprocesses_for：上游对下游输入做预处理。
  • converts_format_for：格式转换关系。
  • parameterizes_for：上游为下游产生参数。
  • filters_candidates_for：过滤候选集合。
  • ranks_or_scores_for：评分/排序关系。
  • validates_output_of：验证另一个工具的输出。
  • refines_output_of：细化另一个工具输出。
  • reports_or_summarizes：汇总报告关系。
  • alternative_to：替代方案，默认不作为 chain edge。

边建立规则

  • 单向调用：A→B 和 B→A 是不同判断，每个 allowed direction 单独判定。
  • stage 只剪枝：stage 不参与 confidence 打分，只减少明显不合理 pair。
  • confidence：采用 confidence_raw = agent_confidence。
  • 生成类边拆分：完整输入和部分输入分开，避免把“部分可用”误当作可直接执行。
  • requires_intermediate：不再作为 edge_type，只作为 negative_reason，避免把“还缺中间步骤”误画成可用边。
  • sidecar：复杂解释写入 edge_debug_sidecar.jsonl，主图字段保持瘦身。

3.2 raw session 里有什么：训练需要的是其中一部分

会进入训练语义的 block

  • text/thinking：可转成 <thought> 或最终说明。
  • MCP tool_use：工具名形如 mcp__molclaw-scp__*，是药筛工具调用。
  • MCP tool_result：可转成 <observation>，用于后续推理上下文。
  • final text：可转成 <final_answer>。

不会作为药筛工具学习的 block

  • Bash、Read、Write、Edit、Grep、Glob 等工程工具。
  • 读 skills、看目录、写 run_log.md / result.md 的工作流 chatter。
  • 本地绝对路径和长文件列表通常不应原样进入训练正文。

进入审计而不是正文的内容

  • 原始工具名映射。
  • 被丢弃 block 的原因。
  • 完整 artifact path / base64 / 超长 observation。
  • answer-hit、metrics、accepted/rejected 统计。

4.2 ReAct messages 的组装规则

system
给模型任务身份、输出协议、可用工具约束。
user task
原始任务问题，可能来自 MolBench、KG sampled、E2E。
assistant
<thought> + 一个或多个 <tool_call>。
user observation
工具结果被包装成 <observation>，通常不计 loss。
assistant final
<thought> + <final_answer>。

保留逻辑

  • 自然语言科学推理保留为 <thought>，但应尽量去掉读 skills、写文件等工程 chatter。
  • MCP 工具调用保留为 <tool_call>{json}，工具名前缀规范化为 MolClaw 工具名。
  • MCP 工具结果保留为 <observation>，可摘要化、路径 artifact 化。
  • 最终答案保留为结构化 <final_answer>，尽量只保留任务答案与必要 evidence。

丢弃/压缩逻辑

  • 非 MCP 工具调用和对应结果不进入模型要学习的工具空间。
  • 外层 fenced block 去掉 wrapper，但保留内部真实内容。
  • /root/...、/home/... 等绝对路径转成 artifact handle，原值进入 sidecar。
  • base64、完整 PDB/CIF、超长文件列表、fpocket 全输出应摘要化。

SFT 参数约束为什么要画进流程注释

这不是普通运行说明，而是影响 owner 判断“训练路径是否真的可复现”的关键约束。当前 SFT 路径要求一次 rollout 交给训练的数据量至少能组成一个 global batch，因此：

ROLLOUT_BATCH_SIZE >= GLOBAL_BATCH_SIZE
ROLLOUT_BATCH_SIZE % GLOBAL_BATCH_SIZE == 0
GLOBAL_BATCH_SIZE % DATA_PARALLEL_SIZE == 0

4B 长样本场景下，TP=1 会在 logits/logits.clone 阶段显存峰值过高；TP=4 能解决 GPU OOM，但可能触发 host RAM / Ray memory monitor 问题。因此运行图中要把 smoke/debug 资源约束与正式流程分开。
